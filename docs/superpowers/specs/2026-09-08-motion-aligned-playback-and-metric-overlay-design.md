# 동작 정렬 재생과 지표 시각화 설계

작성일: 2026-09-08

## 배경

리포트 화면에는 서로 다른 두 정렬이 공존한다.

- **재생**: 프로 스켈레톤을 동작 시작 시점만 맞추고 **실제 타이밍**으로 흘린다
  (`SkeletonOverlayPlayer.tsx`의 `proFrame` 계산).
- **점수**: 구간 내부를 고정 step으로 **리샘플링**해 같은 진행률의 자세끼리 비교한다
  (`similarity.compute_similarity`).

즉 **사용자가 보는 것과 점수가 말하는 것이 다른 기준 위에 있다.** 화면에서 두 스켈레톤이
어긋나 보여도 점수는 좋을 수 있고, 그 반대도 가능하다.

구간 상세 지표도 같은 문제를 안고 있다. 지표는 "가속 구간의 85% 지점"처럼 **진행률로**
측정 순간을 정한다. 그런데 "이 순간 보기"로 이동하면 사용자 쪽만 그 프레임으로 가고,
비교 쪽은 재생 시간에서 파생된 다른 프레임을 보여준다. **화면의 두 자세가 지표가 비교한
두 자세가 아니다.**

여기에 지금 답하지 못하는 질문이 하나 걸려 있다. 프로 6명의 같은 지표 값이 이렇게 나온다.

```
stride_arm_slot  [113°, 134°, 167°, 102°, 48°, 82°]
```

이것이 **투수마다 실제로 다른 폼**인지(팔이 일찍/늦게 올라오는 차이는 잘 알려져 있다)
아니면 **측정 오류**인지 판단할 방법이 없다. 숫자만 봐서는 갈리지 않는다. 측정에 쓴 관절과
각도를 스켈레톤 위에 그려주면 눈으로 즉시 갈린다.

## 목표

- 화면 정렬을 점수와 같은 기준(구간 진행률)으로 맞춘다. 실시간 보기도 남긴다.
- 지표가 **어느 관절을 어떻게 재는지** 스켈레톤 위에 보여준다.
- 그래서 지표가 자기 자신을 설명하게 하고, 위 질문을 사용자가 직접 판단할 수 있게 한다.

## 범위 밖

- **분석 알고리즘을 바꾸지 않는다.** 구간 검출·지표 계산은 그대로다. 이 작업은 이미 계산된
  것을 정확히 보여주는 데까지다.
- **판정(양호/주의) 표기를 이번에 바꾸지 않는다.** "프로와 다른 것이 나쁜 것은 아니다"라는
  별도 논의가 있고, 이 시각화가 그 판단의 근거를 제공한다. 순서상 시각화가 먼저다.
- **새 지표를 만들지 않는다.**

# Part 1 — 동작 정렬 재생

## 정렬 규칙

구간별 선형 대응이다. 사용자 프레임 `fu`가 주어지면:

```
fu가 속한 구간 p를 찾는다  (p.userStartFrame ≤ fu ≤ p.userEndFrame)
t  = (fu - p.userStartFrame) / (p.userEndFrame - p.userStartFrame)
fp = p.proStartFrame + t * (p.proEndFrame - p.proStartFrame)
```

구간 경계는 경계로 대응되므로 이어붙여도 **연속**이다. 이것은 점수가 쓰는 리샘플링과 같은
규칙이며, 지표의 `userFrame`/`proFrame`도 같은 규칙(`phase_frame`)으로 뽑힌다. 따라서
**정렬된 화면에서 지표의 측정 순간은 자동으로 양쪽이 맞는다.**

## 서버 변경이 필요 없다

앱은 이미 구간 경계를 받고 있다 — `analysisApi.ts`의 `PhaseScoreDetail`에
`userStartFrame`, `userEndFrame`, `proStartFrame`, `proEndFrame`이 전부 있다. 다만
`mapReport.ts`가 화면 모델(`PhaseScore`)로 옮길 때 `phaseName`과 `score`만 남기고 버린다.
**받아놓고 안 쓰는 데이터를 연결하기만 하면 된다.**

## 폴백

정렬을 만들 수 없으면 **지금의 실시간 정렬로 되돌아간다.** 화면이 비는 것보다 낫다.

- `phaseScores`가 없거나 비었을 때
- 사용자 구간 길이가 0일 때(`userEnd == userStart`) — 그 구간은 `proStartFrame`으로 보낸다
- 프로 구간 길이가 0일 때 — 실측에서 실제로 나왔다(3번 프로의 가속 구간 0프레임).
  이 경우 그 구간 전체가 한 프레임에 대응된다. 정상이며 폴백이 아니다.
- `fu`가 첫 구간 앞이거나 마지막 구간 뒤일 때 — 양 끝으로 고정(clamp)

## 모드 전환

**리샘플링(동작 정렬)이 기본이다.** 화면과 점수가 같은 기준을 쓰게 하는 것이 목적이므로,
기본이 아니면 목적을 반만 달성한다.

플레이어 컨트롤에 토글을 둔다: `동작 정렬` / `실시간`. 실시간은 템포 차이(내가 프로보다
빠르다/느리다)를 보는 용도로 남긴다. 선택은 화면을 벗어나면 초기화한다 — 기억할 만큼
중요한 설정이 아니고, 저장하면 "왜 이렇게 보이지"의 원인이 하나 늘어난다.

# Part 2 — 지표 시각화

## 계약 변경

각 `phaseMetrics` 항목에 `userJoints`와 `proJoints`를 **추가**한다.

```json
{
  "key": "acceleration_arm_slot",
  "label": "암슬롯(상완 기울기)",
  "unit": "degree",
  "userJoints": ["right_shoulder", "right_elbow"],
  "proJoints": ["left_shoulder", "left_elbow"],
  ...
}
```

**양쪽을 따로 보내는 이유는 손잡이가 서로 다를 수 있기 때문이다.** 우완 사용자가 좌완
프로와 비교하면 같은 지표라도 사용자 쪽은 `right_*`, 비교 쪽은 `left_*`를 재고 있다.
하나만 보내면 비교 쪽 스켈레톤에서 엉뚱한 팔을 강조하게 된다. 두 배열의 길이와 순서는
항상 같다.

**앱이 관절을 유추하게 두면 안 된다.** 투구 팔이 어느 쪽인지는 서버가 `throwing_side`를 보고
정하며(`joint_name()`), 앱이 따로 유추하면 언젠가 서버와 다른 답을 낸다. 서버는 이미 알고
있고 보내지 않을 뿐이다 — `phaseMetrics`, `unit`에 이어 세 번째다.

관절 이름은 앱의 `SKELETON_JOINTS`와 **정확히 같다**(`left_shoulder`, `right_elbow` …).
그대로 `frame.points[...]`에 넣을 수 있다.

## 기하는 관절 개수가 정한다

| 배열 길이 | 의미 | 그리는 것 |
|---|---|---|
| 1 | 축 지표(높이·거리) | 그 관절만 강조 |
| 2 | 몸통축 대비 각(암슬롯) | 두 관절 강조 + 상완 벡터 + **몸통축 점선** + 호 + 각도 |
| 3 | 세 점 사이각(굽힘각) | 세 관절 강조 + 두 벡터 + 가운데 꼭짓점의 호 + 각도 |

기하를 가리키는 별도 판별 필드를 두지 않는다. 규칙 종류가 곧 배열 길이를 정하므로, 길이를
복제한 필드는 언젠가 서로 어긋난다.

**몸통축을 반드시 그려야 한다.** 암슬롯은 상완이 **몸통축에서** 벌어진 각이라, 관절 두 개만
강조하면 "무엇에 대한 각도인지"가 화면에 없다. 앱이 골반 중점 → 어깨 중점으로 직접 계산한다
— 서버가 body y축을 정의하는 방식과 같다.

## 각도가 화면과 일치하는 이유

각도는 body-frame 정규화 좌표에서 계산되고 화면은 이미지 좌표다. body-frame은 이미지
좌표의 **평행이동 + 회전 + 등방 확대**이므로 각도가 보존된다. 좌완 반전(`mirror_x`)도
각도 계산이 부호에 무관해(`abs(cross)`, `abs(upper_x)`) 영향이 없다.

따라서 **이미지 좌표 위에 그대로 그려도 서버가 보낸 숫자와 그림이 일치한다.** 앱이 각도를
다시 계산하지 않는다는 뜻이기도 하다 — 서버 값을 라벨로 쓴다.

## 탭 동작

"이 순간 보기"를 누르면:

1. **재생을 멈춘다.** 측정 순간을 검증하는 것이 목적이므로 흘러가면 안 된다.
2. 사용자 스켈레톤을 `userFrame`으로 옮긴다.
3. 비교 스켈레톤은 Part 1의 정렬 규칙에 따라 자동으로 `proFrame`에 도달한다.
   **실시간 모드일 때는 `proFrame`으로 고정한다** — 그러지 않으면 화면의 두 자세가 지표가
   비교한 두 자세가 아니게 된다.
4. 양쪽에 기하를 그린다. 각 스켈레톤에는 그 쪽의 값(`userValue` / `proValue`)을 라벨로 단다.
5. 강조는 유지된다. **재생을 누르면 해제된다** — 정지 상태에서의 한 순간에 대한 표시이므로,
   움직이기 시작하면 그 각도는 더 이상 맞지 않는다.
6. 다른 지표의 버튼을 누르면 그쪽으로 바뀐다.

## 관절이 가려진 경우

`SkeletonSvg`는 신뢰도가 `CONFIDENCE_THRESHOLD` 미만인 관절을 그리지 않는다. 기하에 필요한
관절 중 하나라도 그 상태면 **선과 호도 그리지 않고**, 대신 "이 프레임에서는 관절이 가려져
표시할 수 없습니다"를 띄운다. 반쯤 그린 그림은 잘못된 각도로 읽힌다.

지표가 `unavailable`이면 "이 순간 보기" 버튼 자체가 이미 없다(`userFrame`이 `null`).

## 저장소별 변경

### analysis (분석 서버)

`phase_metrics.py`가 각 항목에 `userJoints`와 `proJoints`를 싣는다. 값은 이미 계산된다.

- 축 지표: `[joint_name(pose, rule.joint_role)]`
- 굽힘각: `throwing_shoulder` / `throwing_elbow` / `throwing_wrist`를 해소한 이름
  (순서 고정, 가운데가 꼭짓점)
- 암슬롯: `throwing_shoulder` / `throwing_elbow`를 해소한 이름

사용자 포즈와 비교 포즈에서 **각각** 해소한다(`joint_name(user_pose, ...)`,
`joint_name(pro_pose, ...)`). 두 사람의 손잡이가 다르면 이름도 달라진다.

### backend

`PhaseMetricDto`에 `userJoints: List<String>? = null`, `proJoints: List<String>? = null`.
Jackson 3는 선언되지 않은 필드를 조용히 버리므로 이 두 줄이 없으면 앱까지 도달하지 않는다.

### Frontend

- `analysisApi.ts` / `report.types.ts`: `userJoints`, `proJoints` 추가
- `mapReport.ts`: 위 두 필드 전달, **그리고 `PhaseScore`에 네 개의 구간 경계 전달**(Part 1)
- 새 유틸 `motionAlign.ts`: 구간 경계로 사용자 프레임 → 비교 프레임 대응. 순수 함수
- `SkeletonOverlayPlayer.tsx`: 정렬 모드 토글, `proFrame` 계산을 정렬 규칙으로 교체,
  포커스 상태 관리(일시정지·해제)
- `SkeletonSvg`: 강조 관절·벡터·몸통축·호·라벨 그리기. `react-native-svg`의 `Line`,
  `Circle`, `Path`, `Text`로 충분하다
- `PhaseMetricRow.tsx`: "이 순간 보기"가 프레임과 함께 지표 정보를 올려보낸다

## 알려진 한계

**정렬은 구간 검출만큼만 정확하다.** 구간 경계가 틀리면 정렬도 같이 틀린다. 실측에서 3번
프로의 가속 구간이 0프레임으로 나온 적이 있고, 프로 6명 전원이 구간 경고를 1~2건씩 달고
있다. 이 작업은 그 문제를 고치지 않는다 — 다만 **틀린 것이 눈에 보이게 만든다.** 그것이
지금 필요한 것이다.

**각도는 단일 카메라의 2D 투영각이다.** 팔이 카메라 쪽으로 오거나 멀어지면 실제보다 짧게
찍혀 각도가 왜곡된다. 화면에 그린 각도도 같은 왜곡을 갖는다 — 숫자와 그림은 일치하지만
둘 다 투영각이다.

## 검증

- **Frontend (Part 1)**: `motionAlign` 순수 함수를 컴파일 후 node로 검증한다
  (`formatMetric.ts`와 같은 방식). 구간 경계에서 정확히 대응되는가 / 구간 중간이 선형인가 /
  사용자 구간 길이 0에서 나눗셈이 터지지 않는가 / 프로 구간 길이 0이 한 점으로 접히는가 /
  범위 밖이 양 끝으로 고정되는가 / `phaseScores`가 없으면 `null`을 돌려 폴백을 부르는가
- **Frontend (Part 2)**: `npx tsc --noEmit`, `npx expo export --platform android`.
  그리기 로직은 테스트 러너가 없어 실기기 확인이 필요하다
- **analysis**: `userJoints`/`proJoints`가 손잡이에 맞게 해소되는가 / 길이가 규칙 종류와
  맞는가(축 1, 암슬롯 2, 굽힘각 3) / 기존 지표 값이 그대로인가(회귀)
- **backend**: 두 필드 왕복 직렬화, 없을 때 `null`
- **실기기**: 프로 6명의 `stride_arm_slot`을 각각 열어 48°와 167°가 실제로 다른 자세인지
  확인한다. **이것이 이 작업의 목적이다.**

## 열린 항목

- 축 지표(길이 1)는 강조만 하고 기하를 그리지 않는다. "디딤발 착지 폭"이 몸 중심에서 어느
  방향으로 얼마인지까지 그리면 더 좋지만, 기준선 종류가 하나 더 늘어난다. 각도가 먼저다.
- 정렬 모드 토글의 위치와 라벨은 실기기에서 보고 정한다.
- 실시간 모드에서 비교 스켈레톤을 `proFrame`으로 고정하는 것은 그 순간 정렬이 깨진다는
  뜻이다. 정지 상태이므로 문제되지 않는다고 보지만 실기기에서 확인한다.
